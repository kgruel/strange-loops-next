Diagnosis

The model is small. A closed set of about ten folds covers it in roughly 3,600 lines. The codebase around it is about 77,000 lines, and much of that is custody machinery, migration and duplicated storage encodings. The rewrite pays off through what it leaves out more than through the language.

Where Arrival went wrong

The use case is several people writing records and sharing them, which is a multi-writer, merge-by-default problem. Arrival's core invariant is "one lineage has exactly one designated authority," which is single-writer custody. The two conflict.

Performance: what's the language and what's the algorithm

The characterization ledger shows the main costs are algorithmic. Raw append is flat. Everything above it was linear in depth, so filling a store was quadratic.

Times in milliseconds, before the receipt-order change. Receipt order cut held-handle receive by 69% at 1k and 87% at 5k. sdk_emit_fact didn't move, because every emit cold-opens the vertex and replays the whole prefix.

  • The language fixes: CLI cold start (61 ms of Python imports) and constant factors.
  • The language doesn't fix: replay on open. That needs cached state. Start whole-vertex: cache each vertex's state keyed by its spec, its covered set and the tick ids of the vertices it reads, and refold the vertex when any of them changes. Partial rewind to a checkpoint waits until a real store hurts: across vertices that read each other, its invalidation would become the new Arrival.
benchmarks/LEDGER.md

Findings 1 to 6: every write re-folded the entire history; ingest was quadratic; the read path is fine; the SDK's stateless surface is a constant tax; search only covers declared kinds; receipt-order fold-in-place fixed held handles only. Measured 2026-08-15 on one machine. Treat sub-10% deltas as unproven.

How Arrival grew

Sharing knowledge about a large work platform, among colleagues, encoded into git or JSONL, led to "mergeable by default." Arrival answered with a backend-neutral custody protocol: lineages, dense ordinals, hash chaining, compare-and-append, head attestations, and later rollback and equivocation detection, epochs and re-custody.

Receipt order came from the performance work. Folding on (ts, id) made ingest quadratic, so fold order became the order this store received facts. That's store-local by definition, so merge(A,B) and merge(B,A) give different fold sequences. Mergeability then had to be rebuilt on top through custody, which is where the scope spiralled.

docs/RECEIPT_ORDER_FOLD.md and libs/store/src/store/merge.py

"Receipt order is store-local. A rowid means something only relative to the store that assigned it." The merge docstring: "No claim is made about event time, about rowids as a primitive, or about the relationship between merge(A,B) and merge(B,A)."
