Three ways a reader reaches the core
A · local server
  browser, LSP, MCP ──JSON-RPC──▶ loops serve ──▶ .loops/ on disk

B · WebAssembly (the core runs inside the page or extension)
  page or extension [ loops-wasm ] ──▶ browser storage, or files you pick

  Swift, Kotlin [ loops-ffi, through UniFFI ] ──▶ the app's own storage

WebAssembly is a compact bytecode browsers run natively, so a library's own code runs inside a page with no server. A suits a laptop and keeps keys out of the browser. B suits the annotation extension, static hosting and an offline web app. C suits a phone. All three speak the same JSON shapes, so a front end written against serve moves to B or C without changing what it sends.

  • Pure functions plus a thin handle. The pure half is what Lean models and fuzzes; the handle is the only part with I/O.
  • The core takes specs as data: JSON, hashed in canonical form, so formatting never changes a key. See Specs are JSON below.
  • serve speaks JSON-RPC that mirrors the crate. The LSP and MCP are JSON-RPC too, so each is a thin translator, and a JavaScript front end makes the same calls.
  • Refusals are values: code, field and optional batch line. The historical six-code sketch is obsolete. The protocol and fixture contracts define current refusal vocabularies.
  • The envelope's version rides in the signed prefix (loops/record/v1:). A reader refuses only versions newer than it knows, and says so.
  • Watching stays outside the core. The core gives a checkpoint; serve notifies on its own writes at once, hears other processes through file notifications, and polls only as a fallback. The proposed handle runs the pure due check after a record lands. Either the server or the emitting CLI/MCP process runs it. A content tick can run anywhere, since a second run makes the same id; a witness tick runs where its key lives. Remotely, watch(checkpoint) streams over a WebSocket, each connection a handle narrowed to a grant. The client holds its checkpoint, so a dropped connection resumes with nothing lost, and serve keeps no list of subscribers. Between places there is no push: sync pulls, a static place costs one conditional GET, and pings stay deferred until a public store has readers.

Specs are JSON

The historical KDL file mixed storage, producers, selection, parsing and commands. Specs now use JSON with a closed vocabulary. Programs can construct them directly. protocol/spec.md defines the implemented grammar. The example below proposes unsupported product keys. Its $schema path is illustrative and does not name an existing file.

{
  "$schema": "…/protocol/vertex.schema.json",
  "vertex": "manuscript",
  "note": "The book as it stands: the latest prose per chapter, in book order.",
  "from": [{ "store": "novel", "kind": ["chapter-prose", "book-order"] }],
  "fold": {
    "chapters": { "latest-by": "about", "follow": "prev" },
    "order":    { "latest": true, "follow": "prev", "where": { "env.kind": { "is": "book-order" } } }
  },
  "boundary": [{ "when": "draft-complete" }]
}
  • No mapping layer. The file is the data, and its canonical JSON is what gets hashed. KDL's traps go with it: repeated properties keep only the last, so kind="scene" kind="character" meant only character.
  • Proposed schema tooling: editors and MCP could share JSON Schemas. Those schemas do not exist. protocol/spec.md remains normative.
  • Specs are records of kind vertex, so a store carries its vertices. vertices/<name>.json is only the editing form: loops apply emits it, and writing it back is pretty-printing the payload.
  • Comments become note: data, shown by read, on hover and in review. It doesn't shape a result, so it stays out of the input key.
  • Predicates are where maps with six operators: is, not, present, absent, at-least, below. Expression strings such as "approved == children" become {"state": "approved", "at-least": "$size"}. A vertex with params is a template; $name is a literal filled at run time, so predicates stay closed.
  • store.json and places.json are proposed renders of declarations and local places. The design shares JSON across files, records and interfaces. Most people set places with loops place add.

Laws, then vectors, then Rust

settled: Lean 4 The core is a small, closed set of pure functions, which is what a proof assistant is for. An executable model in Lean 4 states the laws the core must keep and proves them. The model then writes the vectors and is fuzzed against the Rust core. Lean never enters Rust's build; what we keep is the laws, the vectors and the scenarios.

Why Lean 4. AWS Cedar combines executable Lean, proofs, Rust and differential testing. Its published review reported 4 proof-discovered bugs and 21 additional testing findings. Lean supplies tactics, bytes, strings and unbounded integers. The protocol model stays outside Rust's build.

What lens proofs cover. Only the syntax we own: the combinators, the escaping, the conflict block. Lenses built from proved combinators inherit the laws, as in BiGUL, verified in Agda; "up to normal form" is a quotient lens. CommonMark at large, editors, how viewers display a file and adapters for other formats stay with tests. That's a reason to keep the owned syntax small: inside it everything is provable.

Historical spike: roughly 220 model lines and 540 proof lines, using core Lean without Mathlib. Its theorems used the standard axioms. Incremental equals batch follows from the step fold; set invariance supplies the stronger law. Count repeats require each id once on the accumulating path. Readers tolerate unknown prev targets. Writers require held targets in the store or batch that share a thing.

Planned cadence: model one step ahead, prove its laws, compute its vectors, then implement it. Do not specify unexplored product behavior. Keep modules reviewable as units.

Required proofs: core meaning laws need proofs under explicit premises. Unproved laws remain labeled conjectures, with vector and differential checks. The build rejects sorry. Passing fixtures does not prove a conjecture.

Hashes, signatures and numbers: standard vectors, not proofs

Runtime checks use external standards vectors, including RFC 8032 for Ed25519 and RFC 8785 number samples for canonical bytes. An explicit proof of shortest formatting and roundtrip remains open. Hashes and signatures themselves lie outside the hash-parametric proofs.

State machines: the fold already is one

A full state-machine framework would coordinate shared mutable state, and the model has none: no consensus, no transactions across writers, records append-only, state always derived. Each vertex is already a state machine (records in, fold as transition, tick out), and the closed fold vocabulary is its definition, written as data. Building a generic engine on top is the accretion the limits exist to stop.

Reference states, boundary modes and tick lifecycles need future transition models and proofs. They are not fully enumerated or proved today. If places later coordinate mutable state, model-check that separate protocol in Quint or TLA+.

Budgets: guard the failure, not the size

settled The old repo didn't fail by being big. It failed because each edge case became more code in the same layer, and size was the symptom. Lines also punish a language's idioms and say nothing about whether anyone can hold the code at once. So instead of one line count, four budgets, each against one failure:

Per module, not per file: meaning defines the unit, whether one file or a directory. File limits reward splitting without reducing complexity. Watch surface growth because small additions rarely leave. Price vocabulary changes through their cache-key version.

Budgets grow through the ledger. An increase needs two independent use cases and a reason outside composition cannot serve them. The number is a tripwire, not a target.

Proposed regenerability test: give a fresh agent the protocol and vectors. Ask it to rebuild one module within its budget. Passing vectors checks agreement on those cases, not complete correctness. Failure can expose missing protocol detail or excessive module scope.

The limits

settled Four tiers: what the model refuses to be, what the core won't contain, what waits for a trigger, and what lives outside by design. Each line names what earned it, so a future "can we just add…" argues with the reason, not the rule.

The rule for the core. Something enters the core only if two separate cases need it and it can't be built outside from records, ticks and lenses. Across six walks, only the lens contract's changes passed: every lens needed them, and the diff runs in the core.

2 · What the core won't contain

Construction ratchets where possible: the forbidden thing can't be expressed, rather than a lint someone enforces.

  • No user code in folds. The fold vocabulary and the predicates are closed; specs have no expression syntax. Extension is collectors in and lenses out.
  • No clock or randomness in folds or lenses: fold functions get no context that holds one; "as of" is an input.
  • The core computes; it doesn't connect. Places are interfaces; HTTP, git and Syncthing are adapters. Comparing segment lists stays in; moving bytes is outside.
  • The core never reads the world: no git, no URLs. Birth keys and URL normalization are tooling.
  • One crypto suite: hashing, Ed25519, salted commitments. A version byte, no runtime choice. BBS and zero-knowledge proofs stay outside. Encryption at rest belongs to the storage medium or a future place adapter.
  • No plugin system: collectors and lens adapters are processes over stdin and stdout.
  • No query language. Vertices are the questions; search is full-text. For ad-hoc questions, open a SQLite place read-only with plain SQL; writes still go through emit.
  • No migrations: records are never rewritten; Arrival's stores arrive through a collector.
  • No parse pipelines: Where, Skip, regex and lambdas move into collectors, which may do anything because their output is records.
  • No effects: boundaries lose run. At a boundary the vertex ticks; an observer watching ticks runs the script.
  • No state-machine framework: each vertex already is one. Records are its input, the fold its transition function, a tick its output.
  • No UI, orchestration, model calls, or authorization beyond admission and grants.
  • Proposed implementation guardrails: forbid unsafe and async core code. Limit macros to derive, match closed enums exhaustively and restrict public traits to storage, signing and lenses.

4 · Outside by design

Keep collectors, lens adapters, LSP, TUI, front ends and orchestration outside the core. Git hooks, merge drivers and place adapters also sit outside it. Lean computes protocol-vector answers and supplies the differential oracle. External standards retain independent expected answers.

Spec predicates: a closed set

Historical predicate review: parse pipelines drifted toward regex and lambdas; boundaries reached shell commands. The legacy session vertex selected kind alone. protocol/spec.md defines current typed tests. Future tick and identity examples below remain proposals.

WhereAllowed
Selecting records (one record at a time, clauses ANDed)Implemented tests compare typed text, sets, safe whole numbers and envelope times. resolve-by, decimal-kind declarations and tick time cuts remain proposed. Sources provide alternatives; tests within a source combine with AND.
Tickinga record of a kind arrives, with the same matches; the vertex's own state crosses a value (high >= 80); count and window modes
Neverregex, substrings, string functions, arithmetic, conditions across records, user functions, effects

Why closed: each operator joins the fold vocabulary, so it enters the cache key, needs vectors and must behave the same everywhere. Regex exposes the risk: Rust and JavaScript engines disagree at their edges. The same records could then produce different folds.

Classify by recording, not by predicate. When a selection needs text matching, judgment or arithmetic, an observer computes it once and records the answer; the vertex selects on the record. The answer is signed, cached and visible in provenance instead of hidden in a filter.
