Building it

Rust, in a new strange-loops repo: a core crate with two allowed dependencies, a CLI crate around it, and a Lean model beside both. The product is the protocol, its vectors and one implementation; other languages meet it at the JSON format, the CLI or a local socket, and phones and browsers can carry the core itself. Steps 0 and 1 are built, and step 2 is modelled and reviewed. Next, the data model is formalized in Lean, before step 3 or any Rust.

Language: Rust

settled: Rust Reversed from Go in version 31. The page had said embedding stopped mattering, because any language can write a signed record in about 100 lines. That holds for writing. A phone app or a browser extension that reads, folding what friends annotated, checking standing and rendering a lens, needs the core itself inside the device, and there Rust is clearly ahead.

  • Why Rust: the core can run where people read, in a phone or a browser extension, with no server; a strict compiler is a fast verifier for agents, since exhaustive enums make whole classes of mistakes fail to compile with a reason; the closed sets and the Lean model's inductive types become enums directly. AWS's Cedar is exactly this stack: a Lean model with proofs, a Rust implementation, differential testing between them.
  • Guards, since cleverness is what Go protected us from: the core is synchronous; #![forbid(unsafe_code)]; no macros beyond derive; the only traits in the public API are the three contracts (Place, Signer, Lens); closed enums are matched without wildcard arms, so adding a fold type makes the compiler list every place that must handle it.
  • Costs, covered: the core can't be dependency-free, since Rust's standard library has no cryptography and we never write our own, so the imports budget becomes an allowlist (sha2, ed25519-dalek); JSON, canonical form and base32 we write ourselves, as in Go; SQLite cross-compiles with cargo-zigbuild; first builds take minutes, kept short by few dependencies.
  • What switching cost: about a day. Step 1's Go was about 3.5k tokens, and the vectors are language-neutral, so the Rust core passes the same vectors and the JS writer still cross-checks it.
  • Dropped: Go (its KDL parser lives on as a standalone release), Zig (pre-1.0, thin libraries), OCaml and Haskell (small ecosystems, less agent fluency), Swift (weak off the Mac).

  • Pure functions plus a thin handle. The pure half is what Lean models and fuzzes; the handle is the only part with I/O.
  • The core takes specs as data: JSON, hashed in canonical form, so formatting never changes a key. See Specs are JSON below.
  • serve speaks JSON-RPC that mirrors the crate. The LSP and MCP are JSON-RPC too, so each is a thin translator, and a JavaScript front end makes the same calls.
  • Refusals are values: one type, a code from a closed enum, the field it concerns and, in a batch, the line. Every surface shows a refusal the same way. Step 1 has six codes (kind-empty, observer-not-typed, emitted-not-rfc3339, about-not-typed, prev-not-record-id, under-not-record-id); the MCP walk added outside-grant.
  • The envelope's version rides in the signed prefix (loops/record/v1). A reader refuses only versions newer than it knows, and says so.
  • Watching stays outside the core. The core gives a checkpoint; serve notifies on its own writes at once, hears other processes through file notifications, and polls only as a fallback. Boundaries run in whoever holds the handle when a record lands, using the pure due check: serve when it runs, otherwise the CLI or MCP process after its own emit. A content tick can run anywhere, since a second run makes the same id; a witness tick runs where its key lives. Remotely, watch(checkpoint) streams over a WebSocket, each connection a handle narrowed to a grant. The client holds its checkpoint, so a dropped connection resumes with nothing lost, and serve keeps no list of subscribers. Between places there is no push: sync pulls, a static place costs one conditional GET, and pings stay deferred until a public store has readers.

Specs are JSON

settled KDL was chosen when a vertex file was the whole runtime: where records lived, who produced them, what to select, parsing and shell commands. A spec is now a few clauses from a closed vocabulary, and most are written by programs: the LSP builds one per hover, MCP one per about, the orchestrator fills templates, stores ship standard vertices, agents create them. So a spec is JSON, defined by a JSON Schema in protocol/, checked against the Lean model's types. KDL leaves the project; its parser, written for step 1, becomes a standalone Go release.

{
  "$schema": "…/protocol/vertex.schema.json",
  "vertex": "manuscript",
  "note": "The book as it stands: the latest prose per chapter, in book order.",
  "from": [{ "store": "novel", "kind": ["chapter-prose", "book-order"] }],
  "fold": {
    "chapters": { "latest-by": "about", "follow": "prev" },
    "order":    { "latest": true, "follow": "prev", "where": { "env.kind": { "is": "book-order" } } }
  },
  "boundary": [{ "when": "draft-complete" }]
}
  • No mapping layer. The file is the data, and its canonical JSON is what gets hashed. KDL's traps go with it: repeated properties keep only the last, so kind="scene" kind="character" meant only character.
  • One schema, three readers. Editors complete and check fields from $schema; agents get the same schema as the MCP emit tool's; programs need nothing but the standard library.
  • Specs are records of kind vertex, so a store carries its vertices. vertices/<name>.json is only the editing form: loops apply emits it, and writing it back is pretty-printing the payload.
  • Comments become note: data, shown by read, on hover and in review. It doesn't shape a result, so it stays out of the input key.
  • Predicates are where maps with six operators: is, not, present, absent, at-least, below. Expression strings such as "approved == children" become {"state": "approved", "at-least": "$size"}. A vertex with params is a template; $name is a literal filled at run time, so predicates stay closed.
  • store.json and places.json follow, as renders of the store's declarations and this machine's places: one format across files, records, --json, serve, MCP and a browser. Most people set places with loops place add.

Laws, then vectors, then Rust

settled: Lean 4 The core is a small, closed set of pure functions, which is what a proof assistant is for. An executable model in Lean 4 states the laws the core must keep and proves them. The model then writes the vectors and is fuzzed against the Rust core. Lean never enters Rust's build; what we keep is the laws, the vectors and the scenarios.

Why Lean 4. The pattern has been run at scale: AWS builds the Cedar authorization language as an executable Lean model with proofs, a Rust implementation, and differential random testing between them. The proofs found 4 bugs and the differential and property tests 21 more, and no release ships unless the model, proofs and tests are current. That is exactly this stack. Lean is mature, has automation (simp, omega, grind) that does much of the routine proving, has bytes, strings and unbounded integers, and is the proof language models are strongest at.

What lens proofs cover. Only the syntax we own: the combinators, the escaping, the conflict block. Lenses built from proved combinators inherit the laws, as in BiGUL, verified in Agda; "up to normal form" is a quotient lens. CommonMark at large, editors, how viewers display a file and adapters for other formats stay with tests. That's a reason to keep the owned syntax small: inside it everything is provable.

The spike: adopted. It took a day, not weeks. About 220 lines of model, 540 of proofs, core Lean only (no Mathlib), and every theorem rests on Lean's three standard axioms alone. Two findings: incremental = batch is free for any step fold, so the law worth proving is that the set decides; and Count counts repeats, which puts dedup by id on the read path. A dangling prev replaces nothing, so it shows as a fork. (Since version 34 writing one is refused, and a reader that hasn't synced the target sees it replace nothing until it arrives.)

The model leads by one step, not the whole protocol up front. Each step in the sequence extends the model and its laws, writes that step's vectors, then builds the Rust. Modelling further ahead than that would be specifying what nobody has walked yet. The model sits under the context budget too: it is the protocol in exact form, so it should come out smaller than the Rust it checks.

Which proofs are required. The executable model and its vectors are required at every step. The laws that define what the system means, "the set decides" and "no false resurrection", must be proved. Others may wait: an unproved law is listed in laws.md as a conjecture, checked by vectors and fuzzing until it is proved, and --wfail keeps sorry out of the build.

Hashes, signatures and numbers: standard vectors, not proofs

The model treats hashing and signing as abstract functions (a hash assumed collision-free), since proving SHA-256 or Ed25519 is not our problem. Their vectors come from the standards: RFC 8032 for Ed25519, RFC 8785 and its number samples for canonical bytes. ECMAScript number formatting is notoriously hard to prove; the round-trip law holds up to it.

State machines: the fold already is one

A full state-machine framework would coordinate shared mutable state, and the model has none: no consensus, no transactions across writers, records append-only, state always derived. Each vertex is already a state machine (records in, fold as transition, tick out), and the closed fold vocabulary is its definition, written as data. Building a generic engine on top is the accretion the limits exist to stop.

Where state-machine thinking does pay is the small finite tables: the five reference states, the boundary modes, a tick's lifecycle. They live in the Lean model, where every transition is enumerated and proved, and the vectors carry them to Rust. If places ever share state concurrently, model-check that one protocol in Quint or TLA+; it sits in "not yet" with that trigger.

Bend 2, considered

Bend 2 is pure, dependently typed and affine, built around laws an AI writes proofs for. Against Lean it loses on what we need: no tactics, numbers limited to Nat, U32 and F32, a compiler its README calls young and mostly AI-written, and a proven kernel that is itself formalized in Lean. A compiler lane into our implementation language would be about 2k lines, but the catch is trust, not effort: proofs cover the source, so a miscompiled fold would carry its proof and still need checking, and it would be a fork of a fast-moving, unaudited compiler. Its WONTFIX.txt is a list of limits in the same shape as ours.

Budgets: guard the failure, not the size

settled The old repo didn't fail by being big. It failed because each edge case became more code in the same layer, and size was the symptom. Lines also punish a language's idioms and say nothing about whether anyone can hold the code at once. So instead of one line count, four budgets, each against one failure:

BudgetGuards againstMeasureLimit

Per module, not per file: a module is the unit of meaning (one file, or a directory with mod.rs), and a per-file budget only rewards splitting files. Surface is the one to watch: re-accretion arrives as small widenings that never come back out. Vocabulary is already priced: version 17 put the fold vocabulary in every key, so adding a fold type invalidates every cached result. That's a construction ratchet: the design itself charges for growth.

Budgets grow only through the ledger. A limit rises only with a ledger entry that cites the rule for the core: two separate cases need it, and it can't be built outside. The number is a tripwire for the rule, not a target.

The regenerability test. The core is specified well enough when a fresh agent, given only this page and the vectors, can rebuild one module inside its context budget and pass the vectors. If it can't, the module is too big or the protocol is too thin, and both are worth knowing. Run it now and then, one module at a time; it makes "the protocol is the product" something you can check.

The limits

settled Four tiers: what the model refuses to be, what the core won't contain, what waits for a trigger, and what lives outside by design. Each line names what earned it, so a future "can we just add…" argues with the reason, not the rule.

The rule for the core. Something enters the core only if two separate cases need it and it can't be built outside from records, ticks and lenses. Across six walks, only the lens contract's changes passed: every lens needed them, and the diff runs in the core.

2 · What the core won't contain

Construction ratchets where possible: the forbidden thing can't be expressed, rather than a lint someone enforces.

  • No user code in folds. The fold vocabulary and the predicates are closed; specs have no expression syntax. Extension is collectors in and lenses out.
  • No clock or randomness in folds or lenses: fold functions get no context that holds one; "as of" is an input.
  • The core computes; it doesn't connect. Places are interfaces; HTTP, git and Syncthing are adapters. Comparing segment lists stays in; moving bytes is outside.
  • The core never reads the world: no git, no URLs. Birth keys and URL normalization are tooling.
  • One crypto suite: hashing, Ed25519, salted commitments. A version byte, no runtime choice. No BBS, no zero-knowledge, no encryption at rest: that belongs to whatever holds the place (an encrypted disk or volume, or later a place adapter).
  • No plugin system: collectors and lens adapters are processes over stdin and stdout.
  • No query language. Vertices are the questions; search is full-text. For ad-hoc questions, open a SQLite place read-only with plain SQL; writes still go through emit.
  • No migrations: records are never rewritten; Arrival's stores arrive through a collector.
  • No parse pipelines: Where, Skip, regex and lambdas move into collectors, which may do anything because their output is records.
  • No effects: boundaries lose run. At a boundary the vertex ticks; an observer watching ticks runs the script.
  • No state-machine framework: each vertex already is one. Records are its input, the fold its transition function, a tick its output.
  • No UI, orchestration, model calls, or authorization beyond admission and grants.
  • No cleverness the compiler can't check: no unsafe, no async, no macros beyond derive, no wildcard arms on closed enums, no traits in the public API beyond Place, Signer and Lens.

Spec predicates: a closed set

settled A predicate is wherever a spec says which records or when to tick. Today they live in three places and were drifting toward a language: parse pipelines reached regex and lambdas, and boundaries reached shell commands. The only real vertex in the repo, apps/loops/session.vertex, selects by kind alone.

WhereAllowed
Selecting records (one record at a time, clauses ANDed)kind from a set; about, through resolve-by; a field equals, is in a set, is present or absent, or the negation; >=, < only on fields the kind types (int, decimal, EDTF date); time cuts as inputs. OR is a set or a second from.
Tickinga record of a kind arrives, with the same matches; the vertex's own state crosses a value (high >= 80); count and window modes
Neverregex, substrings, string functions, arithmetic, conditions across records, user functions, effects

Why closed: each operator joins the fold vocabulary, so it enters the cache key, needs vectors and must behave the same everywhere. Regex is the sharpest case: Rust's regex and JavaScript's engine disagree at the edges, so the core and a JS reader would fold the same records differently.

Classify by recording, not by predicate. When a selection needs text matching, judgment or arithmetic, an observer computes it once and records the answer; the vertex selects on the record. The answer is signed, cached and visible in provenance instead of hidden in a filter.
