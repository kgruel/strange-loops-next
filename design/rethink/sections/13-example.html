A worked example

Every case so far, in one mature setup: six stores across two realms and three machines, plus a bridge to an HOA board. Commands are the CLI's, store files and vertices are their JSON, and ids are shortened (r:a1…). Records a person doesn't type, such as ticks, are described in comments. On disk every record is a JSONL line or a SQLite row.

How the realm composes

A realm is not a store. @home is everything reachable from one name table, under one trust root (kyle's anchor key). That name table lives in a small store of its own, root; every other store keeps its own anchor, definition and places.

@home realm
└─ root          name table + cross-store vertices + spec templates
     name "novel"   → st:n4…      name "wren" → sl:7f…
     name "feed"    → st:f2…      name "HOA"  → r:h1…
     name "homelab" → st:h9…
     vertices: identity · salience · hoa-recap · hygiene
├─ novel         own anchor, own store.json, own places (laptop, NAS)
├─ feed          own anchor, own store.json, own places (homelab SQLite, laptop 90 days)
├─ homelab       …
└─ runs/*        disposable, one per run
  • Membership is a link, not containment. A store belongs to @home because root holds a name record pointing at its st: id. The store doesn't know its realm; joining adds links and never rewrites, so one store could be named in two realms' tables.
  • Names live at two levels. Realm-wide names (stores, Wren, the HOA) live in root. Names local to one store, such as the novel's characters or the team's components, live in that store.
  • Cross-store work lives in root. A vertex reading several stores needs a carrier, and none of the stores it reads is the right one. It resolves store names through root's table, and its ticks land in root unless it says into.
  • Why not one big store: places and formats, stewards and maturity, erasure scope, what you share and with whom, and lifecycle all differ per store. A co-author can get novel without ever seeing feed.

id = hash(canonical(env) + commit) and commit = hash(salt + canonical(payload)), so the second line still verifies, every reference to r:9f3c still resolves, and nothing else in the repository changes.

What the example surfaced

  • A realm needs its own store. @home names a name table, and name records are records, so they live somewhere: the root store. It's also the natural carrier for vertices that read across stores (identity, salience, the HOA recap) and for spec templates.
  • A vertex's ticks default into the store that carries it. The HOA recap lands in root, the incident's ticks in homelab; a run says into explicitly.
  • Collectors split like stores do. Parse specs are shareable and a store can carry them; source bindings and credentials stay in places.json beside the place they write. A parse spec is an ordinary kind: collectors read it, the core doesn't.
  • Natural-key rules are declarations (natural "org" normalize=…), and a same-as between an anchor and a natural key joins minted and natural identity.
  • Relative windows need tick syntax: "window": {"occurred": "last 30d"} in the spec, a concrete span on the tick.
  • "follow": "prev" appears on every facet fold. It should probably be the default wherever records carry prev. Settled in PR 13: it stays written. Latest-by without it is refused (follow-missing), so every spec says whether it reads heads or history.
  • Corrected in version 12: this example used a SKOS match kind. Identity is same-as and dispute; the director's knowledge is a dispute plus a note about both components.
  • Reference-only tick payloads paid off: erasing the note in the team store changed nothing in any tick.
