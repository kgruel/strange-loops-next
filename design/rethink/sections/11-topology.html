Realms

Stores relate in three ways: compose, bridge and replicate. Only replication moves whole stores, and it is the only one that needs merge semantics. Most stores have one writer. Ticks are records that reference what they cover, and they can travel alone or with everything below them. How vertices tick is in Resolution.

Realms and the boundary rule

A realm is a name table plus a boundary rule. @home names a table, not a store: every store has one, a realm has one that links its children, and a domain can optionally vouch for one. Because records hold only hash ids, joining stores into larger realms changes how names resolve and never rewrites data.

Consequence for layer 1: a spec routes and folds records. A route must be able to say "ticks from vertex V" as easily as "records of kind K." A fold over child ticks, like "how many slices passed review," is ordinary.

Why immutable segments instead of a log with a head
  • Git-storable but not git-only. The backend contract shrinks to put, get and list on immutable blobs, compared with Arrival's atomic compare-and-append.
  • Replication is a union of segments. Writers never touch each other's segments.
  • Composition is the same union, at read time. "Combining stores is an ordinary local operation" becomes literally true: compose and merge are one operation at different scopes.
  • Witness order survives without an authority. Each writer's segment chain is that observer's receipt order, hash-linked.

For the team case in git: segments per writer and device, .loops/segments/<lineage>/<device>/, each file closed once committed. Corrected: an earlier version suggested merge=union in .gitattributes as a safety net. With one writer per file an honest pull never conflicts on a segment, so a conflict is an alarm; see Sharing. Decision records get reviewed in the same PR as the code they explain.

Arrival was right to want storage neutrality. The trouble was its unit: an ordered log with a head needs authority, and immutable segments don't.

Privacy falls out of references

Composition and bridging never copy raw records. A salience tick can be shared while the browsing history it covered stays private. For anyone without access, the references don't resolve, and the signature and root still prove the tick is authentic. Email can't leak into a shared repo just because a vertex looked at it.

The hard parts that remain
  1. Resolving a reference across stores. A small locator registry (store name to path or URL); ticks may carry hints. Bundles cover the cross-machine case.
  2. Erasure. A writer can compact its own segments. Record hashes don't change, and ticks that covered an erased record keep their root while that record becomes unresolvable. Design this early.
  3. Declarations in multi-writer stores. Settled per store by convention, not by protocol.
  4. Clock skew. For human-scale stores, emitted plus id tie-breaks is probably enough. A hybrid logical clock is available if not.
