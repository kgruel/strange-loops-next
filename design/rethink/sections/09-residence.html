Layer 4: places

Places owe the layers above very little: list records, get one by id, what's new since a checkpoint, a blob by hash, and a disposable index. Everything else is a per-store, per-machine choice: where segments live, in what format, and how much of the store each machine holds.

layer closed Segment sync between places is a comparison of segment lists; see Sharing.

Discovery walks up to the nearest .loops/, the way git finds .git. Zero-config is .loops/ alone, JSONL, no places.json. The device in a segment path is a label per write place, created on first run; it keeps two writers out of one file, and each segment is signed by exactly one device key. In a git place a segment file closes once it is committed and the next write opens a new one, so a writer on two branches adds two files instead of forking one. A store whose places are all SQLite can be a single store.db holding the same things.

shared: shared places stay reviewable in PRs. refuse: prevention, before erasure is needed. refs: reference fields, once called edges. facet: emitted whole. search: worth indexing; each machine decides. preview: how lenses show it by default. erasable: payloads go to a blob place.

  • Updating a store is an emit. apply compares the file with current declarations and emits one changeset record, so a half-synced replica never sees half a change. Breaking changes are refused (a new kind instead); removals emit retire.
  • It's a performative. A steward's changeset takes effect. Anyone else's is a visible proposal that takes effect if a steward affirms it.
  • Concurrent edits are forks, two heads on prev, resolved by a steward stance. No merge conflicts in a config file.
  • A record is judged by the declarations in effect at its emitted. Raising a store to strict doesn't reject its history. A record emitted before a declaration it would violate, but arriving after it, is flagged: the late-record pattern applied to definitions.
  • The definition has a history: what the store looked like in 2021 is a fold over its declarations.

Places

A place is a location, a format and a scope, holding segments. The store is the union of its segments across places. Remixing is safe because ids are computed over canonical bytes (JCS), not a file format; segments are immutable and single-writer, so sync is union; and ticks already say what they saw, so partial places stay honest.

RoleMeaning
writewhere this machine appends its own segments
holda copy of segments, whole or scoped (scope by emitted, never occurred, or late records go missing)
blobswhere large or erasable payloads live

The index isn't a place: it's derived and per machine. What the remix enables: git as interchange (JSONL in git for sync and review, SQLite as a fast working copy), tiering (recent on the laptop, everything on the homelab, cold in object storage), erasable payloads in a blob place outside git, and backups that are just places.

The index holds envelopes and byte offsets, never payloads. Full-text search uses SQLite FTS5 contentless tables (the inverted index only; contentless_delete lets erasure remove rows), opt-in per kind. The store declares which fields are worth searching; each machine decides whether to build it.

Erasure

The need that matters: private data that shows up where it shouldn't, usually fine at home but landed in a shared store. Retraction is a status (retire); a leaked secret must be rotated anyway. So erasure acts per store, and stays small.

PieceWhy
Hash the payload separately, salted, per payloadids, ticks and what they cover survive erasure; the salt stops anyone confirming a guess
One reserved kind, erase, signed by a steward, per storea visible gap, not a broken reference
Tick results reference, don't copynothing inside ticks needs chasing
The envelope is permanentpersonal identifiers go behind opaque anchors, never natural keys in about

The whole game: find every record holding the data (search, then trace references from the originals), emit erase for each, and each store replaces the opening with the commitment. In git that means a steward rewriting one segment file's history; because ids never change, nothing else is touched. Rejection isn't erasure: policy hides a record from folds, but in git it still exists.

Prevention, before cure
  • Promotion is a deliberate stance, so it's the review moment; agent-proposed promotions need yours.
  • Store policy can refuse whole sources ("never admit records from personal collectors").
  • A hygiene vertex flags likely-personal payloads (emails, phone numbers, health terms) for the stale review; secret scanning sits in the same place.
What true erasure would look like

A record shouldn't contain its data; it should commit to it. hash(salt + payload) is a hiding commitment; erasure is forgetting the opening.

3 · Topologythe referencesnothing, but it rewrites other records and breaks immutability
  • Keeping references is what makes erasure finishable. The hard part is everything derived from a record; surviving references let a hygiene vertex trace them.
  • Physical media: on SSDs deletion isn't reliable, which is why NIST SP 800-88 accepts cryptographic erase.
  • Other parties: what someone has read in plaintext, they can keep. True erasure across parties exists only where content never left your control: the realm boundary rule, "references cross, content doesn't", is also the erasure design.
  • The exotic end: per-field salted digests (IETF SD-JWT) allow field-level erasure; a facet split gets the same result without it. Chameleon hashes (redactable blockchains, Ateniese et al. 2017) swap content under the same hash, at the cost of a master key over all history.
