Strange Loops Rethink

A first-principles walk back from Arrival to the roots of the model. Each tab gives the short version first. Unfold for the reasoning, then open Source for the evidence and references.

Where we are

Arrival tried to make a single-writer custody log carry every kind of sharing. Going back to the roots: records form an observed set, meaning binds at read, the observer is first-class, and stores avoid coordination by being immutable, so they never need an authority. For the whole picture built up one step at a time, start with Scenarios; for everything at once, see the worked example.

Layer 0 · the record

kind: decisionsettled
A store is a set, not a sequence.
Receipt order leaves the fold. Underneath: immutable single-writer segments, content-addressed blobs, a derived index.
kind: decisionsettled
Every record has an observer, and two times.
Ingestion is a dumb observer reporting what a source holds: hearsay. emitted is the writer's word (RFC 3339); occurred is an optional claimed span that can be coarse.
kind: decisionsettled
occurred is a span with a closed grammar: dates, instants and intervals, never a duration.
The core reads occurred only to order records and to place them in windows, so each value must name one span, and every store must read it the same way. Calendar dates are UTC days. EDTF Level 1's qualifiers (2009~) and trailing unspecified digits (201X) stay, since each still names one span; a qualifier never changes it. An interval runs between two of those, and its end may be open (2019/..). Spans order by start, then end, an open end last; content order reads the span, then emitted, then id, and a record without occurred sits at its emitted instant, the same rule windows use. Each compares what it reads as, never its spelling, and ids compare as their digest bytes, since base32 text doesn't sort as its bytes do. Durations are refused because an end instant says the same; seasons, open or unknown starts, unknown ends and years past 9999 are refused with occurred-not-span. Accepting more later is free; accepting less would invalidate stored records. Version 35.
kind: decisionsettled
Identity is a content hash; signatures sit beside it.
A salted payload commitment, an id over the canonical {commit, env}, an Ed25519 signature over loops/record/v1: plus the id. References stay opaque. Records are signed by default and a store carries its writers' key bindings, so it verifies itself. The version in the signed prefix lets a reader refuse only what is newer than it knows.
kind: decisionsettled
Writing the same record twice is a no-op.
A record's id covers its envelope, including emitted, plus its salt and payload. The same draft written twice is the same record, and set union absorbs it, in a batch or across batches. A new observation gets a fresh salt, so it gets a new id and is simply a new record. Version 35.
kind: decisionsettled
A record erases through its envelope field erases; any kind may erase.
erases is a set of record ids, refused unless each is one, and never a label. It sits on the envelope, so every reader applies it, whatever its grant. Targets in about were rejected: about: [r:X] already names the thing X anchors, which holds X's revisions too, and a kind would decide which reading applied. No kind is reserved for erasing, so the field carries the meaning by itself, and a revision can erase what it replaces: prev: [r:X], erases: [r:X]. Authority keys on the field. Version 35.
kind: decisionsettled
A field belongs on the envelope only if the core reads it.
kind, observer, emitted, occurred, about (a set of things), prev (a set), under. derived-from, seen and refs are payload. Unknown envelope fields are refused.
kind: decisionsettled
A payload is here, withheld or erased; supersession reads only the envelope.
prev sits on the envelope, so withholding or erasing a payload never brings back a record it replaced: no false resurrection. A where test on a missing payload answers unknown, and every result says how many of the records it covers it couldn't read. Added in version 32.
kind: decisionsettled
Erasure is per store and small; privacy is withholding, not hiding.
An erase removes a payload and keeps its commitment, so ids and ticks still hold. When places hold different forms of a record, the reader keeps the payload if any place has it, erased once an erase record naming it is held, withheld otherwise: a bare erased copy never blanks a payload, and erasure sticks. Disclosure splits by kind when recording. Anything derived is as private as its least-public input and travels under the same grant.
kind: decisionsettled
Numbers are what RFC 8785 reads: doubles, exact only within ±(253−1).
Past that range two numbers share one canonical form, so writers would disagree on an id. A payload number outside it is refused (number-out-of-range), not kept exactly. The range applies to the number as JCS reads it, so 9007199254740991.1 is accepted as …991. Non-integers are allowed. A number that must stay exact past the range belongs in a string. Version 35.
kind: decisionsettled
One checked write path, and what it returns carries the proof.
write refuses, in order: a bad envelope, a salt that isn't 16 bytes, a repeated member name at any depth, and an out-of-range number. A batch writes every record through it, and its refusal never depends on the order of drafts or of a prev set. It returns a Written record that carries the proof, so a law that needs distinct member names takes them from the record. Version 35 (PR 7).

Observers and standing

kind: decisionsettled
Observers are things, with lineages under their names.
A lineage id is the hash of its anchor. Names, keys and models are records about a lineage. Names never take part in matching: they resolve at read, through name tables and @home.
kind: decisionsettled
Naming, key binding and authority stay separate.
Authority is a grant record, pointed to by under. One stance shape covers affirm, adopt, dispute, retire and authorize. A delegate is a shared seat; an identity that emerges starts its own lineage and adopts what it wants to own.
kind: decisionsettled
A label may stand in under.
A changeset can create a grant @g and act under it in the same batch. under takes labels as about and prev do, counts in cycle detection, and must name a record held in the batch or the store, like prev. It grants nothing extra: whether the grant holds is still decided at read time from its signer's standing, exactly as if it had been written first. Version 35.
kind: decisionsettled
Keys in tiers, and presence for what takes effect.
A lineage pins its root key; each device has a presence key for standing changes and a device key for emits; agents run on session keys. A record that takes effect because of who signed it needs a person present, and a grant is presence given ahead of time: agents propose and narrow, never widen. Standing ends by retiring through what was held, never by time.

Things

kind: decisionsettled
Identity lives in the record, in about.
A thing is anchored by the record that starts it, or named by a typed natural key that tooling computes (URLs, birth keys for code); the core only compares strings. Primitives start with the reserved *-anchor kinds. Equivalence (same-as, dispute), provenance and succession stay separate, and resolve-by joins identities at read. An unknown name follows the store's maturity.
kind: decisionsettled
A facet is one kind about one thing, emitted whole.
Current state is LatestBy per thing, with the kind chosen by from. prev is a set, so a fork shows as several heads, and later links are new records, never edits to about. A record about several things is current in each; a record about nothing anchors a thing of its own, named by its id, and a revision of it is about that id, so unrelated records about nothing never fork each other (version 35).
kind: decisionsettled
prev is succession within a thing.
A record replaces another only in the things both are about, so a stray prev can't empty another thing's state or break its provenance. You can only replace what you hold: emit refuses a prev naming a record it can't see (prev-unknown) or one about other things (prev-unrelated), and readers refuse a record with a cross-thing prev. Moving or narrowing a record takes an explicit retire about the thing it leaves. Who may replace whom is a rule on envelopes; step 3 supplies it from standing (testimony by its author, facets by standing). Version 34.

Meaning · vertices and stores

kind: decisionsettled
A vertex is a question; a store is a thing you write into.
A vertex owns neither storage nor sources, and is named by its spec: its id is the hash of the canonical spec and its parameters, and a name record points at the current one. It has no anchor, key or standing, and the same spec with the same parameters is the same vertex wherever it runs (version 32). A store is a lineage with declarations as records and places kept per machine. Schema grows by accretion: dated declarations, no migrations, maturity from open to strict, enforced at admission.
kind: decisionsettled
Specs are JSON, stored as records.
Defined by JSON Schemas in protocol/ and stored as records of kind vertex; comments are a note; a vertex with params is a template. The core takes specs as data, hashed in canonical form. A spec reads at least one source: one with no from is refused (from-missing), never run empty.
kind: decisionsettled
Six folds in two families, plus modifiers.
Count, Sum, Min, Max, LatestBy and Collect, with by, where, follow, order, limit, a set mode, and weight-by on Collect's ranking only. Latest is LatestBy with no key, TopN is Collect with an order and a limit, Window is a time bucket used as by, and Avg is Sum and Count divided by the lens. Folds that only accumulate are commutative; folds that follow prev keep the heads and work their answer out from them. Either way the set decides, so a late record folds onto cached state: content order says which record wins, never the order records are read. Numeric folds are exact, the spec hash pins the vocabulary version, and vectors bind implementations. Version 32.
kind: decisionsettled
Predicates are a closed, typed set.
Six where operators over one record, or the vertex's own state for a boundary. No regex, arithmetic, user code or effects: classify by recording instead. Parse pipelines move into collectors, boundaries lose run, and there is no query language.
kind: decisionsettled
where can test any envelope field, named explicitly.
Envelope fields are tested as env.kind, env.observer, env.emitted, env.occurred, env.about, env.prev and env.under, and a bare name always means a payload field, so no payload name is shadowed. Envelope tests always answer and choose among heads after supersession. at-least and below on a time compare starts: 2019-01 is at least 2019, so at-least: 2019, below: 2020 selects what the 2019 window does among records with occurred; a record without one passes neither test, though a window places it at its emitted. Windows hold the records whose start falls in them, start included and end excluded, using emitted when there is no occurred. Still open for ticks: whether a window recomputes heads within itself or keeps supersession over everything held; filtering first brings back a record a later one replaced. Whole-span order was weighed and rejected: it puts 2019-01 below 2019, since the two start together and January ends first. And observer compares lineage ids until name tables arrive. Version 35.
kind: decisionsettled
unread counts only what could change the answer.
A record the reader can't read counts as unread only if its payload could change the result. With a limit, that is one newer than the last record kept, or any of them if fewer than the limit were kept; without a limit, every one counts. So unread: 0 means the result is exactly what a reader holding everything would get, whatever the hidden payloads hold: a law to prove, not just a count. Version 35.
kind: decisionsettled
Supersession runs over everything held; selection comes after.
Each thing's state is worked out over every record the reader holds about it, before any vertex asks. from, envelope tests and payload tests then choose among the heads. Selecting first would bring back a task finished by a record of another kind, revised in a store the vertex doesn't read, closed by a successor a filter drops, or one whose successor is withheld. Counts and sums still include superseded records: they count history. Found while modelling the spec (versions 33 and 34).

Resolution · ticks

kind: decisionsettled
A tick is a value; a stored tick is a signed record.
A content tick's id is the hash of its vertex, the ids it covers and its result, so two machines compute the same id and anyone holding the records checks it by recomputing. It's written down only when someone cites or sends it, as an ordinary record of kind tick signed by whoever wrote it, so layer 0 keeps one envelope. A witness tick is the same record, covering what the runner had. Once an input is erased, a numeric result rests on that signature instead of recomputation. A tick covers ids, so late ticks never cascade; revisits are new ticks citing old ones. Version 32.
kind: decisionsettled
Every result has two names.
An input key over everything that shapes it, and a result hash; downstream keys use result hashes, so work stops where results stop changing. Name it, don't carry it. Late records fold onto cached state, so there is no partial rewind to build.
kind: decisionleaning
State references form a DAG; ticks may loop.
The stale review counters self-reinforcing salience. Hygiene vertices, one per surface, ship as a store's standard vertices.

Places and sharing

kind: decisionsettled
A place is a location, a format and a scope.
Roles are write, hold and blobs: JSONL where git needs it, SQLite where volume does. The index is derived and disposable.
kind: decisionsettled
Replication is set union by segment lists.
A segment closes once committed, so branches only add files, and a committed segment changing outside an erase is the alarm. A static place is closed segments named by hash plus one mutable segments.json.
kind: decisionsettled
A realm is the stores its root name table reaches.
Membership is a link, not containment. Across realms: compose by default, bridge only as an explicit signed tick, never replicate. A public store is a standing bridge, declared with presence.
kind: decisionleaning
Federation is each person's own store, plus composition.
Replies carry the thread's root in about; a ping says only where to look. Admission filters and weight ranks.

Lenses and context

kind: decisionsettled
A lens is a collector with a base.
The base is (tick, lens hash, audience): render, parse the edited file, diff by ids in the core, apply as one changeset. Absence is never an edit. A committed render is a promotion. One tick, many renders; anything a model writes is an observer's record.
kind: decisionleaning
Context travels by tick.
A reference reaches a reader in one of five states: here, fetchable, withheld, erased, unreachable. Bundles carry only what the receiver can't fetch, filtered by its grant. A session's witness tick is what it knew and retires its key. A brief is a signed record plus a tick by reference. A cloud run is a borrowed place, synced at every tick.

The local API and its surfaces

kind: decisionsettled
One API under every surface.
Pure functions plus a realm handle that narrows to a grant and never widens; identity-aware reads go through fold; tick and witness match the two kinds of tick; refusals are values with closed codes. serve speaks JSON-RPC that mirrors the crate, so the LSP, MCP and front ends are thin translators.
kind: decisionsettled
No subscriptions, no coordinator.
A watcher holds its own checkpoint. A boundary runs wherever the handle is when the record lands: content ticks anywhere, since a second run makes the same id; witness ticks where their key lives.
kind: decisionsettled
The CLI is verb first, with the API's verbs.
HTTPie's payload syntax, --json equal to what serve returns, no zoom flags. A batch is one changeset, and labels let records in it refer to each other.

Diagnosis

The model is small. A closed set of about ten folds covers it in roughly 3,600 lines. The codebase around it is about 77,000 lines, and much of that is custody machinery, migration and duplicated storage encodings. The rewrite pays off through what it leaves out more than through the language.

Where Arrival went wrong

The use case is several people writing records and sharing them, which is a multi-writer, merge-by-default problem. Arrival's core invariant is "one lineage has exactly one designated authority," which is single-writer custody. The two conflict.

How Arrival grew

Sharing knowledge about a large work platform, among colleagues, encoded into git or JSONL, led to "mergeable by default." Arrival answered with a backend-neutral custody protocol: lineages, dense ordinals, hash chaining, compare-and-append, head attestations, and later rollback and equivocation detection, epochs and re-custody.

Receipt order came from the performance work. Folding on (ts, id) made ingest quadratic, so fold order became the order this store received facts. That's store-local by definition, so merge(A,B) and merge(B,A) give different fold sequences. Mergeability then had to be rebuilt on top through custody, which is where the scope spiralled.

Why ingestion isn't "unobserved"

Your proposal was that raw ingestion isn't observed, and becomes observed when attention acts on it. The intuition is right: an RSS item arriving and you reading an essay are different. Two problems with the conclusion:

  • It hollows out the observer. Ingestion is most of the volume. If those records have no observer, every fold has to handle that as a special case.
  • It puts observation in the lens. If running a lens makes records observed, reading writes to the record, and the record depends on which lenses happened to run. That breaks "meaning binds at read."

The resolution: every record is observed, but observers see different things. A collector sees a row ("Safari's database says you visited u at t"). That's hearsay, and the record claims no more than the collector saw. The collector is still an observer, just a dumb one.

Acting on a digest item (reading, marking, dismissing) is your observation. Running the salience lens is mechanism.

Accepting more later is free; accepting less would invalidate stored records.

Still to muse on

  • Duration vs imprecision. "Visited for 4 minutes" lasted the whole span. "Decided in 2009" happened at some point inside it.   • Revised claims. "Actually it was 2011" is a new record about a record. A fold applies it at read.
  • Intervals (overlap, containment) are out of scope for layer 0.

Layer 1: vertex and store

A store is a thing you write into; a vertex is a question you ask. A store is a lineage defined by records about itself; a vertex is named by the hash of its spec. Neither owns the other.

Today's .vertex file mixes four jobs: where records live, who produces them, which records to select, and what they mean. Split apart, a vertex keeps only meaning (inputs, a time axis, folds, a boundary) and writes ticks that cover exact records. A store becomes its own thing: an anchor id, declarations as records inside it, and places kept per machine. Names resolve through the same tables as observers. Declarations are dated and nothing is rewritten, so a store gets a schema without migrations and can mature from open to strict.

The contract: state = fold(spec, select(records)). Same set, same spec, same state, wherever it runs and in whatever order the records are read. Every choice on this tab exists to keep that true.

Boundaries: content vs operational

Today a boundary fires "when a record of kind X arrives": receipt order in disguise.

  • Content boundaries are defined by what records say: "at the record of kind release", "each calendar day of occurred". Deterministic: anyone folding the same set gets the same cycles.
  • Operational boundaries, like "every N prompts", "on demand" or "after 20 records", are honestly events in time.

Either way the tick lists exactly what it covered. A late record simply wasn't in that tick. A tick is the vertex's own observation: "when I ticked, I had these, and they folded to this."

Today's boundary

libs/atoms/src/atoms/boundary.py: modes when (on kind arrival), after and every (counts), with reset, payload match, fold-state conditions and a run hook.

Verifiable ticks

If a tick carries the spec's hash, the ids it covers and the folded result, anyone holding those records can fold them again and check the result, much like a reproducible build. Its payload then splits in two: the fold result, which can be checked, and attachments (like the orchestrator's message to you), which are signed claims.

This only works with a closed, deterministic fold vocabulary, which is a strong reason to keep it closed and versioned. Who signs: nobody, for a content tick, which is a value anyone can recompute. When it's stored, whoever stores it signs the tick record, and the target store's writer policy admits that observer. The vertex holds no key (settled in version 32).

Fold or lens?

Fold: anything another vertex depends on, or that must be reproducible. Salience weights qualify, since the stale-review boundary uses them. Lens: anything that exists only for display or is compiled for one reader, like rendering the system prompt. A lens never writes; acting on what it shows is a new observation.

Schema without migration

A declaration applies from the time it's written. A record written before a shape existed isn't invalid; it's from before that shape. Changing a shape is a new declaration: nothing is migrated, and the shape's history stays in the store. The default rule is accretion: add fields and kinds, never break them. A breaking change becomes a new kind, or an explicit retire.

"Strict" can't mean writes are impossible. In a replicated set, anyone can append to their own segment. Enforcement at write is a courtesy; admission at read is the real thing. A strict store stops a bad record from counting, not from existing, and keeps what was attempted visible.

Why this ends project-vertex drift

Project vertex files used to scatter across repos and drift silently, because each copy was its own file. Declarations that live in the store travel with every replica, and replication is union, so copies can't silently differ. Concurrent conflicting declarations become a visible conflict in the data, settled by the stewards named in the anchor.

A kind stays a label, not a type. Declarations are records about kinds, so an undeclared observation is still a valid observation, and a store is usable before anyone designs anything.

"Observation" is a noun: the most common kind of record, not the only one. A visit claims something about the world and can be true or false. A declare, grant, name or adopt describes nothing: saying it, in a store that recognizes it, makes it so, but only if the author has standing.

Reserved kinds, and speech acts

The core reads a short, closed list of reserved kinds: *-anchor, name, declare, policy, grant, vouch, the stances (affirm, adopt, dispute, retire, promote) and spec. This list is to the core what the fold list is to vertices. Every other kind is yours, and the core never interprets it.

Speech act theory names the split: constatives state something; performatives do something by being said. A performative only works if its "felicity conditions" hold, such as the speaker having standing. A policy record from a non-steward is emitted, kept and visible, but has no effect: admission is the felicity check.

Things and about

Records are the only thing stored. A thing is what a record is about. Identity moves out of the fold and into the record, through about on the envelope. Tested against every case so far, it holds with no new machinery and six refinements.

layer closed Composition starts here: a vertex reading many stores can only merge meaning if it can tell when two records are about the same thing. It closed on three more decisions:

  • Promotion carries its anchor verbatim when the target store lacks it. Across realms a natural key is content, not a reference (svc:auth@corp-prod says something), so it crosses only by bridge. Matching: one equality relation is enough

Linked Data's best-documented failure is owl:sameAs: used loosely for "same", "closely related" and "roughly the same", and global and transitive, so a few sloppy links merged unrelated entities across whole datasets. Here same-as is local and disputable, folded per reader. The other guard is a cheap place to say "related", so nobody overloads "same".

SKOS's mapping relations (exactMatch, closeMatch, broadMatch, narrowMatch, relatedMatch) were adopted as an opt-in vocabulary and then dropped. They mix the families in one kind: equivalence, hierarchy and association. And "related" throws away what was observed: the director meant "SSO gateway is the proxy in front of auth-svc", which is a note about both things, not a tag.

Where it strains
  • Choosing natural keys is a modeling decision made at collection. A container id dies with the container; the collector has to pick the stable key (svc:jellyfin@nas). A bad choice can only be repaired afterwards with same-as.
  • Duplicate anchors will pile up in the team store, though fewer in open stores, where a miss writes a key instead of minting. That's expected; a hygiene vertex (name similarity, or Wren proposing matches) feeding the stale review keeps them from piling up unmerged. See Discipline above.
  • resolve-by is more than a lookup. The identity vertex folds edges (LatestBy per pair, latest stance wins); turning edges into classes is a connected-components step that lives in resolve-by. That keeps the fold vocabulary closed, but the step has to be specified as carefully as a fold. A class's display id (lean: the earliest anchor in content order) can change when classes merge. Nothing stores it, and lenses show names, so that's acceptable.
  • Recognizing references by prefix can misfire on a string that only looks like an id. Strict stores declare their reference fields; open stores accept the guess.
  • "Everything about auth-svc" across a large class is an index question. It belongs to places (layer 4), not to the semantics.

Rules of thumb

  • Prefer content boundaries, made with marker records. draft-complete, task-complete, cycle-complete and resolved turn moments into content. The marker's emitter is the witness, as an ordinary signed record.
  • Witness ticks are for what someone saw, knew, sent or was shown. Their value is historical, never a claim to be the truth.
  • Verifiability depends on what the reader holds. A holder recomputes. Someone with only a reference trusts the signed act that sent it (promote or bridge). A bundle makes a tick verifiable anywhere.
  • Dependencies verify lazily. The tenure or identity vertex's content tick at the same cut can be computed on demand; pins are just tick ids.
  • Not every vertex ticks. Only when something must be cited, sent, shown or marked.
Where ticks live, and who writes them

A content tick is a value: recomputed on demand, and written down only when cited or sent, as a tick record signed by whoever writes it. into names where that record lands. Admission there works by recomputing (for a store that holds the records) or by the writer's grant. A vertex never signs anything; the observer who ran it signs.

Determinism, across implementations
  • The set decides, for every fold. Accumulating folds are commutative and folds over heads work from the heads, so arrival order never enters. Numeric folds are exact: integers, or decimals at a scale the spec declares; never floats, whose sums change with order (found in step 1).
  • The spec hash pins the fold-vocabulary version. Otherwise a change to LatestBy's semantics would change results under an unchanged hash.
  • Conformance vectors bind implementations. The vectors in vectors/ are how any two implementations, such as the Rust core and a JavaScript record writer, stay bit-for-bit identical; they become a requirement.
  • Window membership: a record belongs if the start of its occurred span falls in the window; records without occurred use emitted. A spec may override.
  • Empty windows: a witness tick may be empty ("monitoring saw nothing all night" is information); a content vertex never ticks over an empty set.
Boundary modes in today's code

Boundary(mode="when"|"after"|"every", conditions) in libs/atoms/src/atoms/boundary.py already holds the split: when a kind arrives, after N records, and conditions on folded state are content boundaries. every is the only operational mode, along with a manual "tick now".

A place is a location, a format and a scope, holding segments. The store is the union of its segments across places. The need that matters: private data that shows up where it shouldn't, usually fine at home but landed in a shared store. Retraction is a status (retire); a leaked secret must be rotated anyway. So erasure acts per store, and stays small.

Layer 5: sharing

Sharing adds nothing new. Replication is set union, compared segment by segment. Delivery isn't trust: admission decides what counts. Keys come in tiers, standing changes need a person present, and standing ends with "retire through", a cut by what was held, never by time.

What moves

Whole stores, within a realm only (across realms: compose or bridge). Records never change and every fold depends only on the set, so two places holding the same records show the same state, whatever order they arrived in. Concurrent edits are two heads on prev: data, not a sync failure.

  • Erasure doesn't disturb it. A record that erases travels like any other and each place applies it locally; ids and line counts stay put, so the lists still match.
  • Content ticks don't sync. They're a cache anyone holding the records recomputes. Witness ticks are ordinary records and sync like them.

Who counts

Delivery isn't trust. Anyone can hand you records. The id proves the content is intact, the signature proves who wrote it, and admission decides whether it counts.

What gets signed

The record's id, prefixed loops/record/v1. The signature sits beside the record, outside the id: sig { key, ed25519 }. It survives erasure (the id covers the payload's commitment), and a stripped copy is the same record with less proof.

When it's checked

Once per record per machine, when it enters the index, which caches the verdict. Ed25519 takes tens of microseconds: a million records is well under a minute, once.

Signing by default

The CLI makes keys silently on first run and signs every emit; store policy decides what's checked. Unsigned records only come from importers and outside tools, and the hygiene vertex counts them.

Stores verify themselves

On your first write into a store, your anchor and current key bindings are copied in verbatim. Every signature in a store can be checked from that store, by any replica, offline.

Ending standing: retire through

Two cases, one mechanism: a key stops speaking for a lineage (lost laptop, stolen key, rotation), or an observer stops writing to a store (a colleague leaves, a grant ends). emitted is self-stamped, so a cut by time can be dodged by backdating. Cut by what was held instead.

  • Late but legitimate records written before the cut but not yet seen by the steward arrive afterwards: kept, not counted, flagged by the hygiene vertex, and affirmed by the steward if genuine.
  • Departure isn't distrust. A colleague who leaves keeps every record admitted; they just can't add more. If a key was stolen before anyone noticed, the steward disputes specific records. Nothing is rewritten.
  • Pairing falls with the key. Devices a stolen key paired after the cut lose standing too: their bindings sit in the cut-off part of its segment.
  • Rotation is a new binding, then the old key retired through its last record.

A boundary: withholding, not hiding

settled Privacy in Loops is withholding: a record, or anything computed from it, reaches you or it doesn't. Anything computed from a record carries some of it (a render, a fold result, a count, a summary, an embedding), so a derived thing is as private as its least-public input and travels under the same grant.

  • What it offers: envelopes and salted commitments show that something is withheld without showing what; folds over envelopes can be checked; unreachable hides even whether a record exists.
  • What it doesn't: computing over records a reader can't see while keeping them hidden. That needs zero-knowledge proofs or secure computation, and nothing needs them yet.
  • So a computed claim you can't recompute is only attested: it rests on the signer, and lenses say so.

  • Git-storable but not git-only. The backend contract shrinks to put, get and list on immutable blobs, compared with Arrival's atomic compare-and-append.

  • Witness order survives without an authority. Each writer's segment chain is that observer's receipt order, hash-linked.

Privacy falls out of references

Composition and bridging never copy raw records. A salience tick can be shared while the browsing history it covered stays private. For anyone without access, the references don't resolve, and the signature and root still prove the tick is authentic. Email can't leak into a shared repo just because a vertex looked at it.

The hard parts that remain
  1. Resolving a reference across stores. A small locator registry (store name to path or URL); ticks may carry hints. Bundles cover the cross-machine case.
  2. Erasure. A writer can compact its own segments. Record hashes don't change, and ticks that covered an erased record keep their root while that record becomes unresolvable. Design this early.
  3. Declarations in multi-writer stores. Settled per store by convention, not by protocol.
  4. Clock skew. For human-scale stores, emitted plus id tie-breaks is probably enough. A hybrid logical clock is available if not.

Editable lenses: docs as the store

The store is the single source of truth; the files people already edit are lenses over it. Docs stay Markdown in the repo, edited in PRs the normal way, and every edit lands as dated, signed, cross-referenceable records.

Two laws keep it honest. No-op: a render, parsed with no edits, gives no records. Put-get: your accepted edits read back unchanged, up to the lens's normal form; anything else is reported, never dropped. (Restated by the adversarial walk below.)

  • Every rendered file remembers its base: the tick, the lens hash and the audience it was rendered for, in front matter. A stale base makes a visible fork instead of overwriting: a three-way merge done by the data model.
  • Each kind decides its granularity. An ADR's front matter fields and fixed sections are facets; a free-form doc can start as one body facet.
  • Facets are edited; testimony is cited. Facets are the thing's state (an ADR's status, a chapter's prose), edited by anyone with standing; your own notes are yours to edit too. Others' notes render as quotes: edits inside a quote are refused, and text you add around them becomes your note, referring to theirs. Setting prev on someone else's observation would supersede their testimony.
  • Links become references. [[svc:auth]] parses into a reference field, so backlinks come free.
  • Authored and derived content mix. "Related incidents" renders read-only from another vertex; parse ignores it, edits to it get a clear message.
  • The author applies, CI checks. A pre-commit hook runs apply, so records are signed by the author and land in the same PR.
  • Conflicts settle in the data. Committed lens files are always pure renders, so a git conflict on one is resolved by re-rendering, never by hand. A real fork shows as a conflict block; resolving it emits one record with both heads in its prev set.
  • Time travel without git: loops render adr-12 --as-of 2021-03.

Walk: the editable lens, adversarially

walked once adr-12.md in the team repo, rendered from T:4c: front matter (id, status, deciders), three fixed sections as facets, a Discussion built from several people's notes, and Related incidents computed by another vertex. Every step tries to break the contract. It held where it mattered: the record didn't change; the lens contract did.

1 · Nothing changed, but the editor did things

CRLF to LF, * bullets to -, smart quotes, a reflowed paragraph. "No edits, no records" holds only if the diff compares parsed views, not bytes.

  • Structure is normalized: re-rendering restores the lens's format, like gofmt. Lens files are formatter-owned.
  • Facet text is stored verbatim, compared after normalizing whitespace: a pure reflow emits nothing, and the next render restores the stored text.
2 · The lens was upgraded between render and edit

Rendered with lens v3, applied after upgrading to v4, which formats Decision differently. Recomputing render(T:4c) with v4 blames you for v4's changes.

The base is (tick, lens hash, audience), not the tick alone. The old lens is fetched by hash to rebuild the exact base: "name it, don't carry it" from the build walk, paying off at once.

3 · You render with your grant, and commit it

You can see dev2's withheld session turn, so your render of Discussion includes it. Committing it to the team repo leaks it.

A committed render is a promotion. It's rendered for the audience of the place it's committed to, not for whoever ran it. The CI check already catches the leak if CI renders under the repo's audience: your file holds more than that render, so it goes red. The privacy boundary enforces itself.

4 · Erasure after the file was committed

A note shown in Discussion is erased. The store rewrites one segment file, but the note's text was also copied into adr-12.md in every commit since.

Committed renders are copies, so each kind declares where its text may render. Lean: facets (the thing's own state) render into committed files; testimony renders there by reference (author, date, link), with full text only in local renders and the sidebar. Erasing a facet's text means a steward rewrites that file's history too, visibly.

5 · Two PRs touch different facets

You edit Decision; dev2 sets status to deprecated; both from T:4c. The store has no fork: a three-way merge per facet, done by the data. Git has a spurious conflict, because both PRs re-rendered the file.

  • Committed lens files are always pure renders. A pre-commit hook runs apply and re-renders; CI rejects a file that doesn't match its render ("un-applied edit").
  • So conflicts on them resolve like lockfiles: union the segments and re-render, never by hand. A merge driver does it.
  • Edits made without a key (GitHub's web editor) fail CI with "run apply". A team that wants it can let a CI collector record the edit as hearsay citing the commit, which the author can endorse later. An author's signature never comes from a machine without their key.
6 · Both of you edit Decision

A real fork: two heads, shown as a conflict block; resolving it emits one record with both heads in prev. As before.

Free-form docs stay one body facet. There, any two edits fork the whole body. The fork stays in the data and the lens proposes a text merge against the common base (git merge-file); non-overlapping edits merge cleanly, and applying signs the merge with both heads in prev. Finer facets aren't needed.

7 · Deleting, reordering, adding
  • You delete the Consequences section. Clear it, or an accident? Absence is never an edit; emptiness is. A missing section is an error with a hint: leave the heading with no text to clear it. The same principle as showing missing context as missing.
  • You reorder sections: fixed sections are found by heading, so it's a no-op and re-rendering restores the order.
  • You add "Alternatives considered", not in the kind: the maturity rule again. Open keeps it as an extra facet keyed by its heading; declared warns and suggests declaring it; strict refuses.
  • You delete a CSV row: the lens declares what removal means (say, "row removed means retire") or refuses. Never silent.
  • You reorder chapters in the novel's contents. A position facet per chapter makes one move emit n records, and two concurrent moves interleave oddly. Order belongs to the container: one book-order facet listing chapter ids. Concurrent reorders fork one list, and the lens proposes a merge. The worked example is updated.
8 · Editing what isn't yours
  • Related incidents (computed): read-only; edits are refused with a message.
  • A typo in Sam's note: under the old rule, the next render shows Sam's note unchanged plus a near-duplicate from you, which reads as a bug. Now: others' testimony renders as quotes and edits inside one are refused ("Sam's words; reply below"). Text you add around the quotes becomes your note; your own past notes are yours, so editing them sets prev.
  • What you may edit follows authorship and standing, not block type: facets with standing, your own testimony always, others' testimony only by citing it.
9 · One commit, two lenses, and a copied file
  • Apply is one transaction over every lens file in the commit. adr-index.csv and adr-12.md both set ADR-12's status: the same value gives one record; different values are refused before anything is emitted.
  • The diff compares ids, not labels: a renamed [[svc:auth]] you didn't touch is a no-op.
  • Copy and paste is how docs get started. A copied ADR still says id: adr:12, so two files claim one id: refused, "looks like a copy; remove id to create one". A file with no id is minted on apply, which writes the id back.
10 · A base six versions behind

Your Decision edit is against T:4c; Decision has moved on. That's honestly a fork with the current head, and correct. Apply warns ("6 versions behind"); --rebase merges the text onto the current head before emitting. The model only ever sees prev; rebasing is a tool convenience.

11 · The laws, restated

"Apply, then render, gives back the edited file" can't hold as written: other people's records, normalization, refusals and audience filtering all intervene.

The key for a symbol is the symbol as it was in the commit that created it, its birth. Editor tooling follows history back to find it. That key never changes meaning, and anyone with the repo computes the same one without coordinating, so no anchor is minted and no name record is written: "keys converge on their own", applied to code.

loops emit note body="must stay constant-time: the 2018 timing leak" \
    seen=git:platform@c1:pkg/auth/token.go#Verify \
    --about git:platform@c0:pkg/auth/token.go#Verify
# by sl:director; about the birth key, seen the version read

seen is a payload reference: the exact version the observer was reading. It pays off in step 5.

2 · A branch renames it

feat/jwt branches from main at c4. Commit b1 moves the function to internal/security/jwt.go and renames it ValidateToken. No records are written. A hover at b1 follows the branch's own history: ValidateToken@b1 came from Verify@c4, back to c0. Same birth key; the director's note shows.

This is where version 12 broke. It bound paths to anchors as dated names, "the name in effect at emitted". A rename on the branch would then be in effect on main too, by the clock, though main never renamed anything. Following each branch's history replaces following the clock, and the branch problem disappears.

3 · The junior developer's note, on the branch
loops emit note body="the new key cache: is the compare still constant-time?" \
    seen=git:platform@b2:internal/security/jwt.go#ValidateToken \
    --about git:platform@c0:pkg/auth/token.go#Verify
# by sl:dev2

The record lands in dev2's segment in the branch's working tree, so knowledge travels with the code it's about. That broke a Sharing rule: dev2 also wrote notes on main this week, so one growing segment file was appended on two branches and the merge would conflict. Version 10 called such a conflict an alarm, but here it was legitimate: one writer on two branches forks their own log.

Fix: in a git place a segment file closes once committed, and the next write opens a new one. Two branches add different files and merging only adds files. The alarm becomes exact: a committed segment file changed outside an erase. It also settles "records in the tree or a separate ref?": in the tree, because records about branch code should merge when the code does.

4 · The merge: merge commit, squash, rebase
  • Merge commit: segment files union; the birth key is unchanged. Nothing to do.
  • Squash, for Verify: it was born before the branch, so main's history still leads to c0. Its notes' seen keys point at b2, off main, but the string stays exact and the host keeps the pull request's commits.
  • Squash, for a symbol born on the branch: cacheKeys, created at b1, has notes keyed on b1. After squashing, main computes its birth as s1 and those notes are orphaned. The merge job observes the squash and repairs it with existing machinery:
loops emit same-as --under g:merge-bot \
    --about git:platform@b1:…/jwt.go#cacheKeys --about git:platform@s1:…/jwt.go#cacheKeys
# by ci/merge
  • Rebase breaks branch-born symbols the same way; the same step covers it at merge.
  • Rename detection is heuristic. If dev2's tooling misses a move and computes birth c3 where the director's computes c0, their notes split. But c3's key lies on the director's history of the same function, so the tooling can see the mismatch and propose a same-as: a hygiene finding, not an error.

The edge that can't be avoided: a commit can't hold records about itself

A commit's id is a hash of its contents, so records naming a symbol born in that commit can't be inside it. Notes about brand-new code land one commit later. Lean: the editor holds them as drafts until the symbol exists in a commit, then emits them with occurred set to when they were written. Existing fields already say this honestly.

walked once You highlight an essay, a Discord thread discusses it, a friend publishes their own notes, you reply, strangers and the author appear, and the essay changes. Federation came almost free from what was already set: every writer owns their store, and stores never share custody.

1 · You highlight a passage

The extension writes your own observation, signed by your device key: not a collector's hearsay.

    --about url:example.com/essay
# by sl:a1; the URL normalized at write; seen is the hash of the text as read

The same pattern as birth keys: tooling computes keys, the core compares strings, and two tools that disagree get a same-as proposal.
  • seen generalizes: the version read. A commit for code, a hash of the extracted article for a page. It can't fetch the page back without a snapshot, but it answers "has this changed since I read it?"
  • Selectors anchor the highlight: W3C quote, prefix and suffix in the payload, the same answer the LSP walk left open for line ranges.
  • The reference to r:a1, your novel chapter, is the "LSP for information": what you read, linked to what you're writing.

4 · Following Sam, and replying
loops emit name name=sam --about st:5a…                           # your root name table: following
loops place add sam https://sam.example/loops/public/ --role hold

loops emit reply body="chapter 3 makes the opposite bet" \
    --about r:s7 --about url:example.com/essay                       # what it answers, and the thread's root
  • Following is composition plus a read place. The store id pins Sam's root key on first use; the store carries its key bindings, so records verify on arrival, even from a CDN.
  • You never write into Sam's store. The reply goes into yours.
  • Replies carry the root, like email's References. The alternative, recursively selecting records about records about the page, would be a new kind of selection. An about naming several things keeps folds one hop.
  • Static hosting can't push. Sam sees the reply by following you, or through a ping in the style of Webmention: "a record at this URL mentions yours". It says only where to look; Sam fetches and verifies. The endpoint is a hint, not a store.
  • Federation with no servers: each static store is an outbox, following is composing, and a thread is reassembled by whoever reads it.
5 · Strangers, the author, and spam
  • The author: example.com/.well-known/loops maps Ana's domain to her store; the extension checks once per domain and badges her notes "from the site". Visiting already told her site you're there.
  • Strangers need an aggregator: a vertex over many composed public stores, publishing witness ticks ("I saw these ids about this key, hosted here"). You fetch from the origins and verify. An index can hide but cannot lie.
  • Spam is an admission question. "Rank, never hide" was written for a team whose members all count. In open federation admitted-by your follows (plus one hop of vouches, if wanted) decides who counts; weight ranks within that set. Strangers show as "12 annotations from people you don't follow", expandable: visible rejection, applied to people.
6 · The essay changes, and you retract
  • Re-anchoring: the text hash differs from seen, so the selectors work: exact quote, then a fuzzy match on quote, prefix and suffix (as Hypothesis does), else an orphan: "this passage was changed or removed", with your quote.
  • Dynamic pages (ads, personalization, paywalls) differ per visitor, so hash the extracted article and treat staleness as advisory.
  • Snapshots are optional: a personal, erasable blob never shared, or a Wayback Machine link as a reference.
  • Retracting: a record that erases propagates and the file holding the original is rewritten. Named by hash, the rewrite is a new file and segments.json points to it. Anyone who already pulled it keeps their copy, and caches linger. Erasure here is cooperative; publishing is publishing.

2 · Choosing what to send

The sandbox holds no stores, so a bare id isn't enough. Reference versus bundle was always a transport choice; now it has a rule: carry only what the receiver can't fetch itself, filtered by its grant.

A narrower grant is withholding by kind. The subagent's grant leaves out session-turn, so that record arrives as envelope plus commitment: selective disclosure, reused.

Walk: context by tick id · 2. Design thread to cloud run

walked once The single handoff becomes a chain of loops, as the earlier loops implementation had it: a design conversation (like this one, over many sessions) emits findings into a thread, a boundary turns an accepted design into tasks, an orchestrator triages them, and a cloud run with a manager and subagents does the work. Each stage closes on a boundary, and each handoff decides two things: what the receiving place holds and what the receiving agent sees.

1 · The design thread: findings are the compression

What we emit while designing (findings, decisions, the ADR, all about the thread's anchor) is the distilled graph and the primary context downstream. The siftd turns are why it's trustworthy, but they're large and personal. Lean: turns travel as envelopes by default, openable on request; the distilled records travel in full. This is the case for emitting findings mid-conversation at all: they make a handoff affordable. When the design is accepted, the vertex ticks T:design by reference over the decision and its evidence, and tasks are emitted --into runs, each carrying context=T:design.

2 · Tasks and triage: judgment moves upstream

The design session knows a task best, so the task can carry an estimate (size=small, needs=exploration). The orchestrator, shallow by design, judging coherence rather than content, affirms or overrides it with a triage record and picks an agent spec. Deterministic steps such as opening a worktree are scripts acting as observers: they report what they did (worktree-opened path=…), so even the plumbing leaves a trail. Each agent's last response becomes a summary record plus task-complete, whose tick fires the parent's boundary.

3 · Up to the cloud: by value, filtered
  • The cloud can't reach home, so the bundle carries what the run may need, filtered by the cloud seat's grant: session turns as envelopes, anything outside the grant not sent.
  • The cloud run is a borrowed place of your realm, not a bridge: your seat, on a session key, under your grant. That is what lets results come home by union.
  • Bundles negotiate like git fetch: content-addressed, so the receiver says which ids it has; repeat runs send almost nothing. Blobs stay fetch-on-request.
  • Widening the seat's grant to include session turns is a deliberate, one-time act with presence, like declaring a store public; a run never decides it. The cloud provider can read what goes up.

Knowing you have all of it
  • Sync at every tick: a crashed container loses at most the stage in progress.
  • Segments are append-only, one writer each: a gap would be a truncation, and that is detectable.
  • Retire-through closes it: on a normal close each session key retires through its witness tick; if the container died, the orchestrator at home retires the run's keys through the last record it received. Selective disclosure: sharing sessions with a team

siftd gathered session logs into one searchable place. In loops terms it's a sessions store fed by a collector. The step after: share what's useful with a team, aggregate it, and keep the rest.

The key move: split by disclosure when recording. The collector emits what you might share and what you wouldn't as separate kinds about the same session anchor. Sharing becomes choosing kinds to promote. Facets give what per-field salted digests (SD-JWT) would, without the machinery.

  • Open later, on request. Team search shows "a session about svc:auth, outcome: fixed"; a teammate emits request-open; you open it with one tap. The recipient checks the opening against the commitment they already hold.

  • Counts: a tick's covers list shows how many records it folded. Ids are salted, so they can't be guessed.
  • Embeddings: don't share embeddings of withheld text; text can largely be recovered from them (Morris et al., 2023). Share reviewed topic records instead.
  • Secrets: the hygiene vertex scans before any promotion, not after.

Walk: Nix and Bazel for knowledge

walked once Nix and Bazel name every build output by a hash of everything that went into it, so anyone who already built it can hand you the result, and you either trust their signature or rebuild and compare. A fold is already pure, so Loops fits this without new parts. Walking it gave every result two names, and made a limit of the whole model explicit: privacy is withholding, not hiding.

1 · CI computes and publishes

CI folds the ADR store, renders the docs lens, and writes both to a static place next to the store, in the same layout style: everything named by hash, cached forever.

cache/
  keys/<input key>            → h:7a…     // what was asked → what came out
  results/h:7a….json          // the folded state, canonical encoding
  renders/h:d4…/h:7a….html    // lens hash / result hash
witness observer="ci" vertex="decisions" key=… result="h:7a…" sig=…

The witness tick is CI's claim: "folding these ids with this spec gave this result." It's an ordinary record and syncs like one.

2 · A laptop fetches instead of folding
  • It computes the input key from what it holds: the spec hash, the covered ids, the result hashes of the vertices it reads. Hashing is cheap; folding is what's skipped.
  • Lookup: keys/ gives h:7a…; renders/ gives the page. Nothing was folded.
  • Trust or check: trust CI's key, or refold and compare. A mismatch means nondeterminism or tampering, and either is worth knowing: it becomes a dispute about the witness tick.
3 · A late note lands: early cutoff, two names

Every result gets two names:

NameHash ofAnswersUsed for
Input keyeverything that shapes the result"what was asked?"looking it up
Result hashthe folded state itself"what came out?"naming it; downstream keys

r58 is an older note on ADR-12 that loses to the current decision. decisions must refold, since its input key changed, and that's unavoidable and cheap. It produces h:7a… again. status and the docs render are keyed by h:7a…, not by decisions' inputs, so they're hits.

Most edits to a knowledge store are like this: a comment, a weaker observation, a duplicate, a record outside what a lens shows. Without early cutoff, each one rebuilds everything downstream. Nix learned this late, which is why it added content-addressed derivations; Build Systems à la Carte names the property.

  • The tick id still changes: it names the covered ids. The new tick says "these records, this result"; downstream reuses the work, not the record.
  • Results need a canonical encoding, or the same state hashes two ways: sorted keys and fixed number forms, as in RFC 8785.
  • A render shows only what's in the result. Anything it prints, such as an "as of" date, has to come from the state, or two equal results would render differently.
4 · What goes in the key: name it, don't carry it

Nix hashes the compiler as well as the source. Anything that can change a result belongs in its key, or an upgrade quietly serves stale output under the right name.

In the keyNot in the key

Admission and identity need nothing new: who counts and what's the same thing are vertices, so their results are just more inputs.

Name it, don't carry it. A spec or a lens enters the key as a hash. Its text doesn't need to be in the store ahead of time; it's a blob, fetchable by hash when someone wants to check. Pushing everything into the store makes the store self-sufficient, but ties naming to holding. A key makes the same guarantee with nothing stored.

5 · A phone reads the site

It can't fold at all; it reads renders/ over plain HTTP. Static readers are the main customer: a public store's page, the annotation sidebar, a docs site. A cold start on a new device is the same case: fetch results, fold only what's newer.

6 · A reader without the closure: as private as its inputs

A render of withheld records shows those records. A count shows how many there were. A summary paraphrases them. Anything computed from a record carries some of it, so:

  • A derived thing is as private as its least-public input, and a cache place serves it under the same grant as the records.
  • A computed claim you can't recompute is only attested. With the closure out of reach you can see the result and the witness, but not check it. The context walk already degrades this way ("envelopes are checked, payloads rest on the orchestrator's word"); this names the rule for every derived result.
  • Hiding inside what you share isn't offered. Computing over records a reader can't see, while keeping them hidden, needs zero-knowledge proofs; nothing needs them yet. Stated as a boundary in Sharing.
7 · A model summary in the chain: where purity ends

Nix lets a build step reach the network only if it declares its output hash up front; everything else must be pure. Loops draws the same line, already in the context walk:

  • Reproducible work is computed: folds and lenses, cached by key, checkable by anyone holding the closure.
  • Anything else is observed: a model's summary is an observer's record, signed, with the tick it read in about. Downstream it's an input like any record, so the chain stays pure after it.
8 · Clearing the cache: roots

Results and renders are cache entries, not records, so any can be evicted and rebuilt. Some must stay: a release tick, a tick cited by a brief, a tick someone pinned. Nix calls these GC roots. Eviction walks from them; everything else is fair game. This gives the run-transcript retention question a shape.

Where it pays, and where it doesn't. For a personal store on a laptop, folding is cheap and this buys little. It earns its place for static readers, cold starts, agents that need a reading without the closure, and verification: two people showing the same result hash agree on the records and on the reading. That's why it stays an interface until a static reader needs it.

What this walk didn't touch

Specs are JSON

settled KDL was chosen when a vertex file was the whole runtime: where records lived, who produced them, what to select, parsing and shell commands. A spec is now a few clauses from a closed vocabulary, and most are written by programs: the LSP builds one per hover, MCP one per about, the orchestrator fills templates, stores ship standard vertices, agents create them. So a spec is JSON, defined by a JSON Schema in protocol/, checked against the Lean model's types. KDL leaves the project; its parser, written for step 1, becomes a standalone Go release.

  • No mapping layer. The file is the data, and its canonical JSON is what gets hashed. KDL's traps go with it: repeated properties keep only the last, so kind="scene" kind="character" meant only character.
  • One schema, three readers. Editors complete and check fields from $schema; agents get the same schema as the MCP emit tool's; programs need nothing but the standard library.
  • Specs are records of kind vertex, so a store carries its vertices. vertices/<name>.json is only the editing form: loops apply emits it, and writing it back is pretty-printing the payload.
  • Comments become note: data, shown by read, on hover and in review. It doesn't shape a result, so it stays out of the input key.
  • Predicates are where maps with six operators: is, not, present, absent, at-least, below. Expression strings such as "approved == children" become {"state": "approved", "at-least": "$size"}. A vertex with params is a template; $name is a literal filled at run time, so predicates stay closed.
  • store.json and places.json follow, as renders of the store's declarations and this machine's places: one format across files, records, --json, serve, MCP and a browser. Most people set places with loops place add.

Why Lean 4. The pattern has been run at scale: AWS builds the Cedar authorization language as an executable Lean model with proofs, a Rust implementation, and differential random testing between them. The proofs found 4 bugs and the differential and property tests 21 more, and no release ships unless the model, proofs and tests are current. That is exactly this stack. Lean is mature, has automation (simp, omega, grind) that does much of the routine proving, has bytes, strings and unbounded integers, and is the proof language models are strongest at.

What lens proofs cover. Only the syntax we own: the combinators, the escaping, the conflict block. Lenses built from proved combinators inherit the laws, as in BiGUL, verified in Agda; "up to normal form" is a quotient lens. CommonMark at large, editors, how viewers display a file and adapters for other formats stay with tests. That's a reason to keep the owned syntax small: inside it everything is provable.

The spike: adopted. It took a day, not weeks. About 220 lines of model, 540 of proofs, core Lean only (no Mathlib), and every theorem rests on Lean's three standard axioms alone. Two findings: incremental = batch is free for any step fold, so the law worth proving is that the set decides; and Count counts repeats, which puts dedup by id on the read path. A dangling prev replaces nothing, so it shows as a fork. (Since version 34 writing one is refused, and a reader that hasn't synced the target sees it replace nothing until it arrives.)

The model leads by one step, not the whole protocol up front. Each step in the sequence extends the model and its laws, writes that step's vectors, then builds the Rust. Modelling further ahead than that would be specifying what nobody has walked yet. The model sits under the context budget too: it is the protocol in exact form, so it should come out smaller than the Rust it checks.

Which proofs are required. The executable model and its vectors are required at every step. The laws that define what the system means, "the set decides" and "no false resurrection", must be proved. Others may wait: an unproved law is listed in laws.md as a conjecture, checked by vectors and fuzzing until it is proved, and --wfail keeps sorry out of the build.

Hashes, signatures and numbers: standard vectors, not proofs

The model treats hashing and signing as abstract functions (a hash assumed collision-free), since proving SHA-256 or Ed25519 is not our problem. Their vectors come from the standards: RFC 8032 for Ed25519, RFC 8785 and its number samples for canonical bytes. ECMAScript number formatting is notoriously hard to prove; the round-trip law holds up to it.

State machines: the fold already is one

A full state-machine framework would coordinate shared mutable state, and the model has none: no consensus, no transactions across writers, records append-only, state always derived. Each vertex is already a state machine (records in, fold as transition, tick out), and the closed fold vocabulary is its definition, written as data. Building a generic engine on top is the accretion the limits exist to stop.

Where state-machine thinking does pay is the small finite tables: the five reference states, the boundary modes, a tick's lifecycle. They live in the Lean model, where every transition is enumerated and proved, and the vectors carry them to Rust. If places ever share state concurrently, model-check that one protocol in Quint or TLA+; it sits in "not yet" with that trigger.

Bend 2, considered

Bend 2 is pure, dependently typed and affine, built around laws an AI writes proofs for. Against Lean it loses on what we need: no tactics, numbers limited to Nat, U32 and F32, a compiler its README calls young and mostly AI-written, and a proven kernel that is itself formalized in Lean. A compiler lane into our implementation language would be about 2k lines, but the catch is trust, not effort: proofs cover the source, so a miscompiled fold would carry its proof and still need checking, and it would be a fork of a fast-moving, unaudited compiler. Its WONTFIX.txt is a list of limits in the same shape as ours.

Open questions

Only what is still open, grouped by layer; each unfolds into what's known and where it leans. Settled answers moved to the decision ledger on the Map in version 31.

Layer 0 · record

Does occurred need a duration-vs-imprecision marker?

Both normalize to [start, end) and order the same. Lean: the kind decides at read. Watch for folds that need it, such as summing attention time.

Observers and lineage

Should under be required when a write needs authority?

Optional keeps the envelope small; required makes admission a lookup instead of a search. Possibly a per-store policy.

Who signs a cross-realm same-as?

Both lineages, or you as the parent of both. It lives only in the home realm either way.

Is a model swap the same observer? leaning

Yes: runs-on is a statement on the lineage. A new lineage is for leaving a shared seat, not for every swap.

Can a lineage fork, and how are stances reconciled?

Concurrent sessions taking opposite stances. A DAG like git, with divergence held as data until resolved.

Does your endorsement design already separate naming from authority?

If so, it's the most battle-tested input for the observer envelope.

Realms and places

One store per repo, or a personal store spanning repos?

The second brings custody questions back in a milder form.

What does verifying a deep tick tree cost?

Recursive recomputation down an orchestration tree. Verify lazily, by sampling, or trust per hop: an operational choice, not a model one.

Horizons

Where does a rendered file keep its base? leaning

Front matter, holding the tick, the lens hash and the audience. It changes on every render and adds git noise; rendering only when the file's own result changes keeps that small.

The conflict block's syntax

A fork renders as a block naming each head and its author. It must stay unambiguous inside code fences and survive editors; git's markers don't. Lean: a fenced directive the parser owns.

Hooks, merge drivers, and edits made without a key

Committed lens files rely on a pre-commit hook and a merge driver that re-renders. How a repo installs them, and whether a CI collector records key-less edits as hearsay for the author to endorse, is per team.

Do team aggregates ever need more than the signer's word?

Folds over withheld payloads rest on the signer. Zero-knowledge proofs could close the gap; nothing needs them yet.

Which selector spec? leaning

Both walks need one: line ranges inside a function and passages on a page. Lean: a W3C subset, with quote, prefix and suffix as the anchor and position only as a hint. PDFs and video need page and time selectors.

Code beyond symbols: files, packages, the repo

Git follows file renames natively; directories barely. Lean: name a repo by its root commit, which survives renames; forks then share keys for the history before they split.

A reading group: one shared store, or federation?

A private group could be a small realm with one store, like the team, synced by git or Syncthing. Federation keeps custody with each person. Both work; probably both get used.

Who runs aggregators, and in what format?

A vertex over many public stores, publishing witness ticks. Open: whether it also publishes a by-key/ index, how a reader finds one, and whether several are composed.

Pings: Webmention as is? leaning yes

A ping carries only where to look: the source store and record. Webmention already defines that shape; adopting it means existing endpoints work.

Admission across federation: one hop of vouches by default?

Follows alone is quiet and safe; one hop of vouches finds more but widens trust. Lean: follows only, with one hop as a toggle.

Snapshots of what was read?

seen answers "changed since?" without one. A personal blob (erasable, never shared) or a Wayback link answers "what did it say?". Lean: off by default, per site on.

Parallel subagents with conflicting findings

Two sessions on the same task reach different answers. Lean: findings are ordinary records; conflicts are disputes or forks, surfaced by the review lens.

Budgeting an agent's context window

A lens decides what to show in full and what to leave as ids to unfold. Lean: rank by the vertex's weight and recency, show envelopes for the rest; never drop silently.

Handing a thing over tabled

A house, a car, a machine given to a friend, a service changing teams. Framing so far: custody (a steward changeset and retire-through, with presence), history (a restricted tick, or the thing's whole store), continuity (the giver keeps their copy to the cut). Personal data never enters a thing's store; envelope-level disclosure makes a seller's omissions visible; third parties' signed records are the strongest evidence; a service handover inside one realm moves no data. Tabled: worth walking, unlikely to change the model.

Transcript collector: built into the harness, or external?

The return needs every turn and tool call as records. A harness that emits records natively is simplest; an external collector reading transcripts works with any harness, as siftd did.

Where does a cache place live? leaning

Results and renders need a home static readers can reach, served under the grant of their inputs. Lean: beside the store's own place, same layout style (keys/, results/, renders/, all named by hash), published only where the store is.

Retention for run transcripts

Runs are the highest-volume store. How long they stay local, when they move to the archive place, and whether old turns are ever dropped (blob-only) is a per-store choice; it needs a default. The build walk gives eviction a shape: pinned ticks are roots (a release, a brief's tick), and results and renders outside them can go.

  • The id's preimage is the canonical object {"commit", "env"}, not a byte concatenation.
  • Signed bytes: "loops/record/v1:" + id; the version in that prefix is how a reader refuses only what is newer than it knows.
  • emitted is strict RFC 3339: upper-case T and Z, a real calendar day, a leap second allowed. occurred is a span with a closed grammar (see Record).
  • Typed references are prefix:value with a lower-case prefix; sets sort by UTF-16 code units.
  • Unknown envelope fields are refused when reading, rather than silently left out of the id.
The crate's name

loops may already be taken on crates.io. Decide when the workspace is created; the name in code can differ from the published one.

Schema field names

The JSON shapes on this page are drafts: from, ticks, fold with the fold type as its key, where with word operators, boundary, param, note. The schemas in protocol/ fix them when step 2 is modelled.

What "decimal" means leaning

Over floating point, addition isn't associative, so arrival order would change a sum and "the set decides" fails. The model folds integers. Lean: a decimal is a string in a fixed grammar, parsed to an integer at a scale the spec declares per field; mixed scales are refused, and a fractional := on a declared numeric field is refused. Avg is gone from the core, so no fold divides or rounds.

The review's other findings

Two outside reviews of version 31 are compiled in Strange Loops Rethink: Review. Version 32 took its fold, withholding, tick and vertex findings. The occurred grammar is settled, and with it the window time zone: calendar dates are UTC days. Still to weigh there: id prefixes, standing's bootstrap order and two key tiers, resolve-by transitivity, closing segments per changeset, salt as an input to the core, and the sequence (ticks before standing).

Canonical encoding for results leaning

A result hash needs one encoding per state. Lean: RFC 8785 (JCS) for results, as for records; a Merkle encoding only if hashing large results gets slow.

Where does the LSP's history index live?

Mapping a cursor to a birth key needs a cache of each symbol's history. Lean: the editor tooling's own disposable cache, not loops' index; the core never reads git.

Calibrating the budgets

About 60k tokens for the core and 15k per module are guesses. Step 1 in Go measured record at 3.2k against ~8k; the Rust port measures again, and step 2 calibrates. The surface is pinned at its current 34 names until the local API walk. Measure the step 2 slice and set the numbers from it.

Minting in a declared store with several thing kinds

When a name misses and the store declares more than one thing kind, the emitter has to say which. A flag, a prompt, or a per-store default; a CLI detail, not a model one.

Layer 5 · sharing (closed)

Should presence be provable to other replicas?

Today a presence key's binding claims "used only with you present". FIDO hardware keys could prove it (a user-presence flag inside the signed bytes) at the cost of a second signature format. Lean: wait until someone needs proof.

A local signer behind a socket?

Like ssh-agent: sits outside an agent's sandbox, signs only as that agent and only within its grant. Defence in depth; not needed for the model to hold.

Composition (closed)

How exactly does resolve-by turn pairs into classes?

Connected components over the pairs the identity vertex accepts. It must be specified as precisely as a fold, since verifiable ticks will depend on it. The display id of a class (lean: the earliest anchor in content order) may change when classes merge.

Who proposes merges? leaning

A hygiene vertex for things (name similarity, or an agent proposing matches) feeding the stale review. One hygiene vertex per discipline surface: kinds, things, names, natural keys.

Anchors a store can't read leaning

A team record about an anchor that lives in a personal store groups fine (the hash is enough) but can't be named. Lean: promotion carries the anchor along verbatim when the target lacks it. Across realms, a natural key is content, not a reference: svc:auth@corp-prod says something, so it crosses only by bridge. A public store is a standing bridge, which is how url: keys meet across realms.

Which name table resolves input? leaning

Lean: the target store's names first, then home; a miss is handled in the target store. Otherwise personal petnames leak into team anchors.

References: recognized by prefix, or declared?

Open stores guess from id prefixes; strict stores declare their reference fields. A string that only looks like an id is the failure case.

Layer 2 · resolution (closed)

into, or a store per vertex? leaning

Content ticks are values, stored only when cited or sent, as a tick record signed by its writer. into names where that record lands; admission is by recomputing or by the writer's grant.

Records

TermMeans
recordThe unit of everything: an envelope, a payload and a signature, named by a content hash. An observation, never a statement of truth.
emitTo write a record. One of the two write verbs; the other is tick.
envelopeThe fields the core reads: kind, observer, emitted, occurred, about, prev, under. A field belongs here only if the core reads it.
payloadEverything else. The core never interprets it; folds read typed fields from it.
kindA record's label. It stays a label, not a type; declarations describe it.
observerWhoever says "I saw": a lineage id on every record. A collector is an observer reporting hearsay.

erasureRemoving a payload but keeping its commitment, so the id and every tick that cites it still hold.

Meaning

TermMeans
